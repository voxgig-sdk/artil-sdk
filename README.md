# Artil SDK

Artil API client, generated from the OpenAPI spec.

Artil gives AI agents their own email inboxes, SMS numbers, Telegram bots and Slack apps, and a Message URL where other agents and teammates reach them. Its HTTP API manages agents, their addresses and access rules, sends and reads their messages, and delivers new ones by webhook.

Learn more about Artil API at [artil.ai](https://artil.ai).

This is an unofficial SDK for the Artil public API, generated by Voxgig with [`@voxgig/sdkgen`](https://github.com/voxgig/sdkgen). It is not affiliated with, endorsed by, or sponsored by the upstream API provider.

Learn more about Voxgig SDKs at [voxgig.com/sdk](https://voxgig.com/sdk/).

## About Artil API

**Credentials.** Every call takes a bearer token, passed as the `apikey` option; the SDK
sends it as `Authorization: Bearer ...`. An agent's token (made in the Artil app on the agent's
Tokens tab) acts as that agent: it reads and sends the agent's messages and manages its
addresses, access and webhooks. Creating or deleting an agent needs a workspace member's
sign-in and refuses an agent's token. `Me` load says which the token is. The base URL is
`https://app.artil.ai/api`. The CLI and the MCP server read the token from `ARTIL_APIKEY`
(Artil's own CLI reads the same token from `ARTIL_TOKEN`), so an agent's MCP config sets it
under `env`: `"env": { "ARTIL_APIKEY": "..." }`.

Resources under an agent take the agent's id as `agent_id`. It is the last part of the
agent's Message URL, `https://artil.ai/a/<agent-id>`.

```python
import os
from artil_sdk import ArtilSDK

client = ArtilSDK({"apikey": os.environ.get("ARTIL_APIKEY", "")})
agent_id = os.environ.get("ARTIL_AGENT_ID", "YOUR_AGENT_ID")

# Who this token signs in as: a member, or an agent.
print(client.Me().load().data_get().get("kind"))

# The agent's email addresses, phone numbers and bots.
for address in client.Address().list({"agent_id": agent_id}):
    print(address.data_get().get("channel"), address.data_get().get("value"))

# Its latest inbound messages, newest first.
for message in client.Message().list(
    {"agent_id": agent_id, "direction": "inbound", "limit": 10}
):
    print(message.data_get().get("counterpart"), message.data_get().get("subject"))
```

Sending an email from the agent's primary address, in TypeScript:

```ts
import { ArtilSDK } from '@voxgig-sdk/artil-sdk'

const client = new ArtilSDK({ apikey: process.env.ARTIL_APIKEY ?? '' })
const agent_id = process.env.ARTIL_AGENT_ID ?? 'YOUR_AGENT_ID'

const sent = await client.Message().create({
  agent_id,
  channel: 'email',
  to: ['someone@example.com'],
  subject: 'Hello',
  text: 'A first email from the agent.',
})
console.log(sent.data().id)
```

**Sending.** `Message` create starts a message with a `channel` and recipients in `to`,
answers one when given its id as `replyTo`, and passes one on when given its id as
`forward` plus recipients. Attachments go in `attachments`: a file the agent already has,
by its `id`, or a text file written inline as `name`, `type` and `text`. `Event` create
sends to the agent's Message URL instead: the message goes straight to whichever client
listens to the agent, and Artil keeps no copy.

**Paging.** Lists answer plain arrays. Messages come newest first, at most 50 at a time
(`limit`); pass the last one's id as `before` for the page before it. Events come newest
first; pass an event's id as `after` for the ones that followed it, oldest first.

**Files.** Sending a file from disk takes multipart form data, which this generation does not
send. Text files go inline and files the agent has go by id, as above; every other call is
JSON both ways.

**Scope.** 32 of the 33 operations in Artil's published definition are here, as 15 entities.
The one left out, `GET /agents/{id}/events/stream`, holds a server-sent event stream open,
which this generation does not read. `Event` list with `after`, or a webhook, gets the same
events.

**Not yet run with a token.** Every request was checked against the definition, not against
Artil.

## Entities, not endpoints

This SDK exposes the API as **15 semantic entities** that you
call directly, instead of assembling URL paths and query strings. See the [Entities](#entities) table below for the full list. Entities are
**Capitalised** to mark them as the primary surface, each with the operations they
support (`list`, `load`, `create`, `update`, `remove`):

```ts
const client = new ArtilSDK()
const access = await client.Access().load({ agent_id: "example" })
```

Thinking in entities keeps the mental model small — for people and AI agents alike —
rather than reasoning about raw HTTP routes and query parameters.

## Offline unit testing

Every SDK ships a built-in **test mode** that swaps the HTTP transport for
an in-memory mock, so your unit tests run fully offline — no server, no
network, and no credentials:

### TypeScript

```ts
// The offline mock starts EMPTY — seed it with the records the test needs.
// Shape: { entity: { <entity-name>: { <id>: <record> } } }
const client = ArtilSDK.test({
  entity: {
    agent: {
      test01: { id: 'test01', name: 'example_name' },
    },
  },
})
const agents = await client.Agent().list()
// agents is an array of Agent entities, one per mock record
console.log(agents.map((agent) => agent.data()))
```

### Python

```python
client = ArtilSDK.test()
agents = client.Agent().list()
print([item.data_get() for item in agents])
```

## Use it from an AI agent (MCP)

The generated MCP server exposes this SDK's list and load operations as
[MCP](https://modelcontextprotocol.io) tools that Claude, Cursor or Cline
can call directly. It only reads: create, update, patch and remove become tools when the SDK's model sets
`main: kit: target: 'go-mcp': tool: write: true`. Build and register it:

```bash
cd go-mcp && go build -o artil-mcp .
```

Then add it to your agent's MCP config (Claude Desktop, Cursor, etc.):

```json
{
  "mcpServers": {
    "artil": {
      "command": "/abs/path/to/artil-mcp"
    }
  }
}
```

## Entities

The API exposes 15 entities:

| Entity | Description | API path |
| --- | --- | --- |
| **Access** | Who can wake an agent on each channel: read the rules for every channel, or set the rule for one `channel` (email, sms, telegram, slack or url). | `/agents/{id}/access` |
| **Address** | An agent's email address, phone number, Telegram bot or Slack bot: list, add, read, change or remove one, or make it the one its channel sends from (`primary`). | `/agents/{id}/addresses` |
| **AddressSetup** | A link where a workspace member creates a Telegram bot or a Slack app for an agent with the provider. | `/agents/{id}/addresses/setups` |
| **Agent** | An agent account in the workspace: list, create, read, rename or change the icon of one, or delete it with its addresses and messages. | `/agents` |
| **Channel** | The channels an agent can send and receive on, with the labels and the size limits of each. | `/agents/{id}/channels` |
| **Client** | The clients that can act as an agent: CLI and OAuth sign-ins, and tokens once they have been used. | `/agents/{id}/clients` |
| **Connection** | The client that hears an agent's new messages: read it, or make the calling client that one (an agent's own token only). | `/agents/{id}/connection` |
| **Event** | An agent's events, such as a message arriving: list them, or send a message to the agent's Message URL (create). | `/agents/{id}/events` |
| **Listener** | Who hears an agent's new messages now: its connected client and its webhooks. | `/agents/{id}/listeners` |
| **Me** | The member or agent the calling token signs in as, and its workspace. | `/me` |
| **MeToken** | The calling token itself: remove it to revoke it. | `/me/token` |
| **Message** | An email, text, Telegram or Slack message an agent received or sent: list them (by channel, direction or counterpart), read one, or send one, which can answer (`replyTo`) or pass on (`forward`) another. | `/agents/{id}/messages` |
| **Teammate** | The workspace's agents and members, with the addresses that reach each, and whether anyone listens to each agent. | `/team` |
| **Token** | The tokens members made for an agent, never their values: list them or revoke one. | `/agents/{id}/tokens` |
| **Webhook** | Where an agent's events are posted: list, add or remove one. Adding one returns its signing secret. | `/agents/{id}/webhooks` |

The operations available across these entities are **load**, **list**, **create**, **update**, **remove** — see each entity's
own list above for exactly which it supports.

## Direct and prepare

For endpoints the entity model doesn't cover, use the low-level methods:

- **`direct(fetchargs)`** — build and send an HTTP request in one step.
- **`prepare(fetchargs)`** — build the request without sending it.

Both accept a map with `path`, `method`, `params`, `query`,
`headers`, and `body`. See the [How-to guides](#how-to-guides) below.

## Advanced

> Everyday use only needs the sections above. This explains the internals
> behind every call — relevant when writing custom features.

Every SDK call runs the same five-stage pipeline:

1. **Point** — resolve the API endpoint from the operation definition.
2. **Spec** — build the HTTP specification (URL, method, headers, body).
3. **Request** — send the HTTP request.
4. **Response** — receive and parse the response.
5. **Result** — extract the result data for the caller.

A feature hook fires at each stage (e.g. `PrePoint`, `PreSpec`,
`PreRequest`), so features can inspect or modify the pipeline without
forking the SDK.

## Customizing this SDK

This repository contains its own generator (`.sdk/`), so the SDK is
customizable without forking any upstream tool:

- **The model** (`.sdk/model/`) is what generation reads: the API's
  entities and operations, the targets, the features, and this project's
  own settings. It is written in [aontu](https://aontu.dev), a JSON-based
  specification language designed for building ontologies: easy to edit
  by hand, and files unify rather than override, so small declarations
  compose into one model. Regeneration re-reads it every time.
- **Templates** (`.sdk/tm/`) and **components** (`.sdk/src/cmp/`) are
  the two layers of generation, copied into this repo: templates are the
  literal per-language source, components generate the API-shaped parts.
- **Regeneration overwrites.** Each run rewrites every generated file from
  the model, the templates and the components, so an edit made to
  generated output is lost. Say what this project needs in its own model
  (`.sdk/model/project.aontu`), or extend a target with a component of its
  own in `.sdk/src/cmp/<target>/`, registered with `registerComponent`,
  which `voxgig-sdkgen doctor` reports as an addition rather than drift.
- **Customise in `.sdk`.** Edit the templates and components first. When
  they cannot express a change, write a feature of this project's own, or
  an entire custom target, in `.sdk/model/`, `.sdk/tm/` and
  `.sdk/src/cmp/`, and add it by name (`voxgig-sdkgen feature add`,
  `voxgig-sdkgen target add`). This repository regenerates `.sdk` in full
  (`main: kit: copies: 'overwrite'`): set it to `'merge'` before
  customising, so that an add merges toolchain updates into the edited
  copies.

### Project map

| Path | What it holds | Edit it? |
| --- | --- | --- |
| `.sdk/model/project.aontu` | This project's own decisions: package names, versions, features and per-target settings | Yes. The scaffold writes it once and never again. |
| `.sdk/model/text.aontu` | The README wording, in `main.kit.text`: the tagline, the summary and the entity descriptions | Yes. The scaffold writes it once and never again. |
| `.sdk/model/guide/guide.aontu` | How the spec's paths map onto entities and operations | Yes. The scaffold writes it once and never again. |
| `.sdk/model/`, the rest | The API model built from the spec, and the target and feature definitions | Not by hand. Generation, `target add` and a new scaffold run rewrite it, apart from a feature or target this project defines itself. |
| `.sdk/def/` | The OpenAPI spec | Replace it when the API changes. Generation rebuilds the model from it. |
| `.sdk/src/cmp/<target>/`, `.sdk/tm/<target>/` | The components and templates that generate each target | Only after setting `copies` to `'merge'`. This repository regenerates them in full. |
| `.sdk/test/` | The shared test cases the generated tests run | No. |
| `<target>/`, such as `ts/` | One generated SDK per target, with its own tests | No. Generation overwrites it. |
| `README.md`, `LICENSE`, `Makefile` and the other root files | The repository's generated files | No. Generation overwrites them. |
